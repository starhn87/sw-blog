[모토맵](https://motomap.kr)은 지도 앱이라 모든 화면이 위치 질문에서 시작해요. <br />
"내 주변 3km 안에 바이커 카페가 어디 있지?" "이 코스를 달리다 들를 만한 휴게소는?" 이런 질문에 답하는 게 일이에요.

이 글은 그 위치 검색을 데이터베이스(PostGIS)에 맡기면서 배운 것들을 정리한 글이에요.

## 앱에서 계산하면 안 되나요?

처음엔 이런 생각이 들 수 있어요. "장소를 전부 받아와서 앱에서 거리를 계산하면 되지 않나?"

장소가 100개일 땐 그래도 돼요. 문제는 데이터가 늘어날 때예요. <br />
장소가 수천 개가 되면 매번 전체 목록을 내려받아야 하고 그중 대부분은 화면에 보이지 않는 곳이에요. <br />
사용자는 강원도를 달리고 있는데 부산 장소까지 받는 거죠.

거리 계산 자체도 간단하지 않아요. <br />
지구는 평평하지 않아서 좌표 두 개의 차이를 피타고라스로 구하면 오차가 나요. 위도에 따라 경도 1도의 실제 거리가 달라지거든요.

그래서 이 일은 DB에 맡기는 게 최선이에요. <br />
PostgreSQL의 공간 확장인 **PostGIS**는 '이 점에서 3km 안에 있는 행'을 인덱스를 타고 바로 찾아낼 수 있어요. <br />
모토맵의 DB를 PostgreSQL로 정한 가장 큰 이유 중 하나도 PostGIS를 사용하기 위함이었어요.

## PostGIS가 뭔가요?

PostGIS는 PostgreSQL에 **공간 데이터 타입, 공간 인덱스, 공간 함수**를 더하는 extension이에요. <br />
일반 PostgreSQL이 문자열, 숫자, 날짜를 다루듯 위치와 경로, 영역을 하나의 값으로 저장하고 SQL로 분석할 수 있게 해줘요.

- `Point`: 카페나 주차장처럼 하나의 위치를 표현해요.
- `LineString`: 라이딩 코스나 도로처럼 이어진 경로를 표현해요.
- `Polygon`: 행정구역이나 서비스 가능 지역처럼 면적을 가진 영역을 표현해요.

위도와 경도를 숫자 컬럼 두 개에 저장할 수도 있지만 DB 입장에서는 그저 숫자일 뿐이에요. <br />
PostGIS 타입으로 저장하면 "두 장소가 얼마나 떨어져 있는지", "이 장소가 특정 영역 안에 있는지", "이 경로 주변에 무엇이 있는지" 같은 공간 관계를 SQL로 물어볼 수 있어요. 공간 인덱스를 사용해 전체 행의 거리를 매번 계산하지 않고 후보를 빠르게 좁힐 수도 있고요.

### `geometry`와 `geography`

PostGIS에서 자주 쓰는 공간 타입은 두 가지예요. `geometry`는 지정한 좌표계를 평면으로 계산하고, `geography`는 지구의 곡면을 고려해 경도와 위도 좌표를 계산해요. <br />
모토맵처럼 실제 지표면에서 "몇 m 안에 있는가"가 중요한 서비스는 거리 단위를 미터로 다루기 쉬운 `geography`가 잘 맞아요. 경로 위 진행률처럼 평면 기하 연산이 필요한 곳에서는 `geometry`로 변환해서 사용하고요.

### Supabase에서 시작하기

Supabase에서는 Dashboard의 **Database → Extensions**에서 `postgis`를 검색해 활성화할 수 있어요. 그다음 공간 타입 컬럼을 만들고 GiST 인덱스를 추가하면 기본 준비가 끝나요.

```sql
CREATE INDEX places_location_idx
ON places USING GIST (location);
```

이제 `ST_DWithin`, `ST_Distance`, `ST_Intersects` 같은 공간 함수를 일반 SQL의 `WHERE`나 `ORDER BY`에서 사용할 수 있어요. <br />
모토맵에서는 장소를 `Point`로 저장하고, 코스의 좌표 배열은 필요할 때 `LineString`으로 바꿔서 검색해요. 아래에서 두 경우를 차례로 살펴볼게요. 더 자세한 설정 방법은 [Supabase의 PostGIS 가이드](https://supabase.com/docs/guides/database/extensions/postgis)에서도 확인할 수 있어요.

## 반경 검색

장소 테이블의 좌표 컬럼은 숫자 두 개(lat, lng)가 아니라 PostGIS 타입인 geography로 저장해요.

```sql
location geography(Point, 4326)
```

`geography` 타입의 좋은 점은 **거리 단위가 미터**라는 거예요. <br />
지구 곡률을 알아서 계산해주니까 '3000미터 안'을 그대로 표현할 수 있어요. 이 컬럼 위에서 반경 검색은 두 함수면 끝나요.

```sql
SELECT
  p.id, p.name, p.category,
  ST_Y(p.location::geometry) AS latitude,
  ST_X(p.location::geometry) AS longitude
FROM places p
WHERE p.approved = true
  AND p.deleted_at IS NULL
  AND ST_DWithin(p.location, ST_MakePoint(lng, lat)::geography, radius_meters)
ORDER BY ST_Distance(p.location, ST_MakePoint(lng, lat)::geography);
```

- **ST_DWithin** - "이 반경 안인가?"를 판별해요. 거리를 다 계산해서 비교하는 게 아니라 공간 인덱스를 활용할 수 있는 형태라 필터는 이 함수로 하는 게 좋아요.
- **ST_Distance** - 가까운 순 정렬에 써요.

여기서 주의해야 할 점이 좌표 순서예요. <br />
보통 '위도, 경도' 순서로 말하는 게 익숙한데 `ST_MakePoint`는 **경도(lng)가 먼저**예요. 수학의 (x, y) 순서를 따르기 때문이에요. <br />
이걸 바꿔 넣으면 에러 없이 조용히 엉뚱한 바다 한가운데를 검색해요.

거리 계산은 `geography`로 하지만 좌표를 다시 숫자로 꺼낼 때(`ST_X`, `ST_Y`)는 `geometry`로 캐스팅해야 해요. <br />
즉, 계산은 geography, 좌표 추출은 geometry를 써요. 두 타입의 역할이 다르기 때문에 그에 맞게 변환해서 사용하는 거죠.

### Supabase에서는 RPC로 감싸요

Supabase 클라이언트는 편하지만 `ST_DWithin` 같은 PostGIS 함수를 쿼리 빌더로 쓸 수는 없어요. <br />
그래서 위 쿼리를 **DB 함수(RPC)** 로 만들어두고 앱에서는 이름으로 호출해요.

```ts
const { data, error } = await supabase.rpc('nearby_places', {
  lat: latitude,
  lng: longitude,
  radius_meters: 5000,
  category_filter: category ?? null,
});
```

앱 입장에선 위치 검색이 함수 호출 하나가 되고, SQL과 필터 정책은 전부 DB 쪽 한곳에서 관리해요. <br />
이렇게 읽기 로직을 한곳에 모으면 관리하기 편하지만, 스키마가 바뀔 때 함수도 함께 갱신해야 해요. 뒤에서 실제로 놓친 사례를 이야기할게요.

## 코스 경로 주변 장소

모토맵에는 라이딩 코스가 있어요. <br />
코스 상세나 경로 미리보기에서 '이 길을 달리다 들를 만한 곳'을 보여주고 싶었는데, 이건 반경 검색으로는 안 돼요. 코스는 점이 아니라 **수십 km짜리 선**이니까요.

다행히 PostGIS는 선 주변 검색도 같은 함수로 해결돼요. `ST_DWithin`의 첫 인자가 점이든 선이든 상관없거든요. <br />
문제는 코스 경로가 DB에 `[[lng, lat], ...]` 형태의 jsonb 배열로 저장돼 있다는 것이라 이걸 먼저 PostGIS의 선으로 바꿔야 해요.

```sql
WITH course_line AS (
  SELECT ST_SetSRID(
    ST_MakeLine(ARRAY(
      SELECT ST_MakePoint((pt->>0)::float8, (pt->>1)::float8)
      FROM jsonb_array_elements(c.route_geometry) AS pt
    )), 4326
  ) AS line
  FROM courses c
  WHERE c.id = course_id
)
SELECT
  p.name,
  ST_LineLocatePoint(cl.line, p.location::geometry) AS route_fraction
FROM places p, course_line cl
WHERE p.approved = true
  AND p.deleted_at IS NULL
  AND ST_DWithin(p.location, cl.line::geography, radius_m)
ORDER BY route_fraction;
```

흐름은 세 단계예요.

1. jsonb 배열의 좌표 하나하나를 `ST_MakePoint`로 점으로 만들고 `ST_MakeLine`으로 이어서 선을 만들어요. `ST_SetSRID(..., 4326)`은 '이 좌표는 GPS 좌표계'라고 알려주는 표시예요.
2. `ST_DWithin`으로 그 선에서 반경 3km 안의 장소를 골라요.
3. **`ST_LineLocatePoint`** 가 이 쿼리의 하이라이트예요. 장소가 경로의 몇 % 지점에 가장 가까운지 0~1 값으로 돌려줘요. 이 값으로 정렬하면 장소 목록이 **코스를 달리는 순서대로** 나와요. 출발하자마자 나오는 휴게소가 먼저, 도착 직전 카페가 마지막에요.

거리순 정렬이었다면 "코스 어딘가에 가까운 곳" 목록에 그쳤을 텐데 진행률 정렬 덕분에 "달리는 순서대로 들를 곳"이 될 수 있는거죠. <br />

## 시행착오: 삭제한 장소가 계속 보였어요

soft delete를 도입하면서 기존 조회 함수의 조건을 함께 갱신하지 않은 적이 있어요.

장소 제보를 반려하거나 정리할 때 행을 바로 지우지 않고 `deleted_at`만 찍는 soft delete를 도입했어요. <br />
그때 이렇게 판단했어요. "지도와 검색 RPC는 `approved = true`만 반환하니까 삭제 표시만 해도 안전하다."

이 가정은 반려(승인 전) 시나리오에서만 작동했어요. <br />
**이미 승인된 장소를 나중에 삭제하면** `approved = true`인 채로 `deleted_at`만 찍힌 상태가 돼요. <br />
RPC의 WHERE에는 `deleted_at` 조건이 없었으니 그 장소들은 지도에도 검색에도 AI 추천에도 계속 노출됐어요. <br />
데이터를 정리하며 삭제한 3곳이 며칠 동안 그대로 보이고 있었고 AI 챗 응답을 검증하다가 발견했어요.

문제는 RPC를 쓴 데 있지 않았어요. `deleted_at`이라는 새 상태를 추가했는데 그 상태를 해석하는 읽기 쿼리를 함께 바꾸지 않은 게 원인이었어요. <br />
일반 쿼리였어도 같은 조건을 빠뜨렸다면 똑같은 문제가 생겼을 거예요.

쿼리 수정은 간단했어요. 모든 조회 RPC의 WHERE에 `deleted_at IS NULL`을 추가하면 돼요. <br />
읽기 로직이 RPC에 모여 있어서 누락된 조건이 여러 기능에 공통으로 영향을 줬고 반대로 수정 지점도 명확했어요. <br />
새 상태 컬럼을 추가할 때는 쓰기 경로뿐 아니라 그 상태를 해석하는 모든 읽기 경로의 조건도 함께 바꿔야 해요. 모토맵에서는 그 읽기 경로가 RPC였기 때문에 모든 조회 RPC를 점검했어요.

## 마무리: 체크리스트

모토맵에서 PostGIS를 쓰며 배운 것들이에요.

- `ST_MakePoint(경도, 위도)`: 경도가 먼저예요. 순서가 바뀌어도 에러가 안 나서 더 위험해요.
- 거리 계산은 `geography`, 좌표 추출(`ST_X`/`ST_Y`)은 `geometry` 캐스팅해요.
- 반경 필터는 `ST_DWithin`, 정렬은 `ST_Distance`로 역할이 달라요.
- 점이든 선이든 `ST_DWithin`가 다 해줘요. 경로 주변 검색은 선을 만들기만 하면 반경 검색과 같은 문법이에요.
- 선 위의 순서가 필요하면 `ST_LineLocatePoint`을 써요. 거리순과는 다른 '경험 순서'를 만들 수 있어요.
- 새 상태 컬럼을 추가하면 그 상태를 해석하는 모든 쿼리와 함수의 조건을 함께 점검해요.

지도 기능을 만들 계획이 있다면 위치 계산을 앱에서 해결하려 하지 말고 PostGIS를 활용해보세요. <br />
Supabase라면 확장 켜고 RPC 만드는 걸로 간단하게 시작할 수 있어요. 모토맵이 어떤 앱인지 궁금하다면 [소개 글](/blog/motomap)도 읽어보세요.
